# CIVICSIGN — Advanced Admin Capabilities (Frontend + Auth Fix) Plan

## 1) Objectives
- Deliver **support-grade admin tooling** in the separate Admin Portal: per-user diagnostics, password reset link generation (copyable in skip-mode), and secure “enter user account” impersonation via OTP.
- Ensure impersonation works reliably by fixing **auth token precedence** (Bearer header must override cookie).
- Provide a safe UX that prevents accidental privilege escalation (no role promotion from portal) while keeping plan/active management.
- Add a self-serve **Reset Password** page that consumes reset tokens generated by admin/backend.
- Validate end-to-end flows with automated testing after core POC is stable.

## 2) Implementation Steps

### Phase 1 — Core Flow POC (must work before full UI)
**Core workflow:** Admin impersonation via OTP + header-first token precedence.

**User stories (POC)**
1. As an admin, I can request an OTP to impersonate a user and see it on-screen (dev mode).
2. As an admin, I can verify the OTP and receive an impersonation access token.
3. As an admin, I can use the impersonation token to act as the user even if my admin cookie is present.
4. As an admin, I can exit impersonation and return to my admin session.
5. As a support engineer, I can reproduce a user issue inside their account without knowing their password.

**Backend (precedence fix)**
- Update `/app/backend/auth.py:get_current_user` to check **Authorization: Bearer** first, then fall back to cookie.
- Quick regression check: normal cookie sessions still work for non-impersonated users.

**Frontend POC (minimal wiring, no new pages yet)**
- `AuthContext`: add impersonation helpers/state:
  - `startImpersonation({token, targetUser})` (store token + metadata; keep admin token preserved if needed).
  - `stopImpersonation()` (remove impersonation token, revert).
  - `isImpersonating`, `impersonatedUser`.
- Confirm axios interceptor uses the impersonation token when present.

**POC verification**
- Manual: admin login → call request/verify endpoints → set token in localStorage → open `/dashboard` and confirm `/auth/me` matches target user.
- Fix until stable.

### Phase 2 — V1 App Development (Admin UX + Reset Password)

**User stories (V1)**
1. As an admin, I can open a user row and view a detail page with diagnostics and recent activity.
2. As an admin, I can deactivate/reactivate a user and change their plan.
3. As an admin, I can generate a password reset link and copy it to share with the user.
4. As an admin, I can impersonate a user via OTP from the user detail page and clearly see I’m impersonating.
5. As a user, I can open a reset-password link, set a new password, and sign in.

**Admin Portal UX**
- `AdminUsers.jsx`
  - Remove role dropdown (render read-only badge “User/Admin”).
  - Make row clickable → navigate to `/admin/users/:userId`.
  - Keep plan + active controls.
- New page: `AdminUserDetail.jsx`
  - Fetch `GET /api/admin/users/{user_id}`.
  - Sections:
    - User summary (name/email/provider/active/plan/created).
    - Diagnostics block (email_configured, sender_email, email_note).
    - Controls: plan select, active toggle.
    - Password reset: `POST /api/admin/users/{id}/send-reset` with `base_url=window.location.origin` → show link + copy button.
    - Impersonation:
      - Request OTP → show OTP + request_id.
      - Verify OTP → receive access_token → call `startImpersonation`.
- `AppShell.jsx`
  - Show top banner when impersonating:
    - “You are impersonating {email}” + “Exit impersonation” button.
    - Exit calls `stopImpersonation()` + refresh `checkAuth()`.

**Reset Password (public page)**
- New page `ResetPassword.jsx`
  - Reads `token` query param.
  - Calls `GET /api/auth/reset-info?token=...` to show email.
  - Posts `POST /api/auth/reset-password` with new password.
  - Redirect to `/login` on success.

**Routing**
- `App.js`
  - Add route `/admin/users/:userId` under AdminShell.
  - Add route `/reset-password` (public).

**Incremental testing**
- After implementing: run quick manual browser tests for:
  - Admin detail load, reset-link creation, impersonation start/exit.
  - Reset password link end-to-end.

### Phase 3 — Testing & Regression

**User stories (testing)**
1. As an admin, I cannot promote any user to admin from the portal.
2. As an admin, I can impersonate a user and still load all normal app pages.
3. As a user, I can reset password using the admin-provided link.
4. As a normal user, I never see admin-only UI/routes.
5. As a system owner, exports/analytics and signing flows still work after changes.

**Testing steps**
- Backend: already curl-verified endpoints; re-check after auth precedence change.
- Run `testing_agent_v3` (frontend + backend E2E).
- Fix failures and rerun until green.

## 4) Success Criteria
- Admin cannot change `role` from the portal (UI removed + backend blocks).
- Admin can:
  - View per-user diagnostics.
  - Generate a password reset link (copyable in skip-mode).
  - Impersonate a user via OTP and operate as that user.
  - Exit impersonation cleanly.
- `/reset-password` works end-to-end (token → set password → login).
- No regressions in: login, envelopes, templates, exports, AI help assistant.
- `testing_agent_v3` passes for critical flows.
